## Public API and master wiring

- Register `ClownCartridgeProfile.ID`, `rolls()`, and the display name in shared `WeaponPerks`. Until registry integration, selection is intentionally inert. Profile static initialization reads JSON directly and never consults the perk registry.
- Pure `WeaponClownCartridge.selected(ServerPlayer, ItemStack)` validates exact original equipped ownership and the canonical selected base roll. `maximumTarget(WeaponCatalog.Entry)` returns the supported weapon's maximum authorised cap, otherwise 0. Master must combine this cap query with exact selected-perk eligibility.
- `Token acceptedReload(ServerPlayer)` runs **only after successful cycle.startReload**. Capture and keep this exact token in the original runtime reload epoch. Acceptance draws no RNG; another accepted reload revokes the previous token. `Token.NONE` is inert.
- `int target(ServerPlayer, Token)` runs exactly once at the real timed reload's **positive ammo-credit callback** (`inserted=true`), after credit succeeded. It returns an authorised target or 0. It consumes only its own helper token/map entry and RNG state; it never mutates an item or magazine. Original owner object, world, exact held stack and slot, loadout mode, GuardianData object/class, GuardianRuntime object, canonical catalog entry, exact selected Roll, monotonic tick and active token identity must all still match. Repeated, invalid, stale or wrong-owner calls return 0 without sampling RNG.
- Only the completion event calls `target`. Queries/HUD/cap checks, denied reloads, dry runs, cancelled reloads, abilities, Dodge and manual refill emulation must never call it. Master applies `ammo.reloadOverflow(target)` to the original magazine, preserves actual reserve-funded gain, persists the loaded limit separately from legacy ammo debt, saves once and displays actual rounds. A valid target is capacity authority, not a promise of available reserves.
- Master calls `update(player)` at its observation boundary; this retires invalid tokens without rebinding. Call `stowing(player, originalStack)` on actual stow, `changed(player, originalStack)` on reload cancellation/replacement, `edited(originalStack)` on every selected roll edit, `cleanup(player)` on death/disconnect/world/class/Super/loadout changes, and `clear()` on server teardown. These hooks cover same-tick away/back and edit-away/back; pure getters deliberately cannot observe or repair historical transitions. `cleanup` is also an explicit reload-cancellation hook. A stale player object's cleanup does not retire a replacement player object's token with the same UUID.

Check finite reserve conservation separately in master foundation tests.
