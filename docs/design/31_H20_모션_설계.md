# H20 — 헌터 전신 모션과 접촉 계약

## 1. 범위와 현재 인수 경계

2026-10-22. H19 아트를 읽어 **별도 H20 모델**과 런타임 클립을 생성했다.
기존 `h15_` 논리 이름, 원본 Steve 스킨/방어구 리그, UV, 텍스처, 피벗, outliner,
그룹 UUID, 기존 비-H15 `roll`은 보존한다. 새 뼈/메시/텍스처를 추가하지 않는다.
H19의 낮은 Void 준비 루프는 JSON 값까지 그대로 상속하며 공격의 단계별 draw만 재저작했다.

변경 파일:

- `scripts/build_hunter_animation_h20.py`
- `src/main/resources/destiny/animation/hunter_h20.animation.json`
- `art/blockbench/animations/guardian_hunter_h20.bbmodel`
- 이 문서
- 부모가 후속 허용한 `src/test/java/kim/biryeong/destiny/fx/H20AnimationTest.java`

실제 H19 저작 경로는 `art/blockbench/animations/`다. 요청의 `players/` 후보 경로를 새로
만들지 않았다. 모델 식별자는 `guardian_hunter_h20`, 패키지는 **19개 `h15_` 클립**이다.
아트 파일은 비-H15 legacy `roll` 1개를 더해 애니메이션 총20개다.

**접촉 감사 정정:** 초기 `worldPosition()` 기반 1.59블록 간격은 실제 전송값 증거가 아니었다.
BetterModel의 해당 조회는 global 캐시와 local Euler 재구성을 혼용한다. 후속 검사는
`sendTransformation()`이 사용하는 `globalState.current` 스냅샷을 직접 읽는다.
또한 vanilla `DisplayRenderer.ItemDisplayRenderer.submitInner`가 native handed item 변환 **앞에
Ry(180°)**를 적용한다. 이 단계를 누락한 초기 H20 테스트와 반대로 바꾼 JSON은 같은 오류를
공유했다. H19B의 left+90/right−90을 H20에도 복원했다(역사 H19 자산은 불변).
완전한 recipe로 release tick7 접점은 약0.0023블록임을 GameTest 로그에서 확인했다.
이 결과는 화면 인수가 아니다. 모든 intermediate 단계와 ±30° 조준 회귀를 추가하여 검사 중이다.

## 2. 먼저 합의한 시간축 — 최종 계약

20Hz에서 `clip tick = seconds × 20`. 현재 `PlayerAnimations` 원샷의 시작 보간1틱을
포함한 **accepted 시점 이후 elapsed server tick = clip tick + 1**을 표에 적었다.
문서/초기 제안보다 아래 최종 계약을 우선한다. 수류탄 release는 초기 .20초에서 **.15초**로
앞당겨 `HunterSkillTiming.THROW_CONTACT_TICKS=4`와 맞췄다.

| 클립 | 길이 / 보간 포함 총틱 | 접촉·릴리스·표식 (clip → accepted elapsed) |
|---|---|---|
| `h15_super_arc_start` | .50초 / 11틱 | 준비 루프로 연결; 이 클립 자체는 피해 없음 |
| `h15_super_arc_attack` | .60초 / 13틱 | .20초: clip4 → **5틱 contact** |
| `h15_super_arc_end` | .35초 / 8틱 | .25초: clip5 → **6틱 item-hide** |
| `h15_super_solar_start` | .45초 / 10틱 | 준비 루프로 연결; 탄 소비 없음 |
| `h15_super_solar_attack` | .35초 / 8틱 | .10초: clip2 → **3틱 shot**; .15–.20초 recoil |
| `h15_super_solar_end` | .35초 / 8틱 | .25초: clip5 → **6틱 item-hide** |
| `h15_super_void_attack` | .90초 / 19틱 | .30초: clip6 → **7틱 release** |
| `h15_grenade` | .55초 / 12틱 | .15초: clip3 → **4틱 throw** |
| `h15_melee` | .40초 / 9틱 | .15초: clip3 → **4틱 contact** |
| `h15_throw` | .40초 / 9틱 | .15초: clip3 → **4틱 throw**; 범용 high cast |
| `h15_melee_solar` | .40초 / 9틱 | .15초: clip3 → **4틱 knife release** |
| `h15_melee_void` | .40초 / 9틱 | .15초: clip3 → **4틱 smoke release** |
| `h15_roll_forward/back/left/right` | 각 .70초 / 15틱 | .20/.30/.40초: clip4/6/8 → 5/7/9틱 접촉 포즈; .50초 발 디딤 |
| `h15_super_arc` | 1.60초 / 준비 loop | 시작/끝 같은 자세; 보간2틱인 기존 ready modifier는 부모 소유 |
| `h15_super_solar` | 2.00초 / 준비 loop | 동일 |
| `h15_super_void` | 2.40초 / H19 준비 loop | H19 값 그대로 보존 |

Arc의 **deploy11/contact5/recovery13**, Solar의 **deploy10/contact3/recovery8**은 부모의
`SuperAttackTiming`과 합의한 수치다. 재입력이 recovery를 끊을지, 피해/탄 소비/프로젝트일을
정확히 어느 서버틱에 전달할지, 취소/죽음/차원 이동 시 pending 작업을 버릴지는 부모 게임플레이
구현 책임이다. 회피의 이동/무적 시작은 별도 gameplay marker이며 위 시각 접촉 포즈와 같지 않다.

저속 TPS에서 BetterModel 재생 벽시계와 gameplay 서버틱이 달라질 수 있다는 H19 관찰은
해결했다고 주장하지 않는다. 표는 정상20Hz 설계 계약이며 저속 TPS 인수 결과가 아니다.

## 3. Arc — 예비 회전 → 타격 → 회수

- 비대칭 하체 지지, 허리/가슴 counter-turn, 앞을 보는 머리, 두 팔로 긴 지팡이를 지지하는
  낮은 guard를 기준으로 삼았다. 오른손 item bone에 장비를 붙이는 기존 계약을 유지한다.
- .05–.10초: 작은 반대 방향 coil. .15초: 팔만 흔들지 않고 흉곽과 어깨가 함께 전진.
  .20초: 전방 수평에 가까운 긴 지팡이 contact. .25–.30초: follow-through 유지.
  .40–.60초: 가슴·팔·망토를 차례로 회수하고 같은 guard로 돌아간다.
- 저작 좌표에서 staff 로컬 +Y 축을 사용한다. attack의 기존 실루엣 key와 오른팔/item의
  로컬 보간 궤적은 보존하고, `.025초` 간격 25개 전신 회전 key에서 왼팔 지지 IK를 다시 푼다.
  목표는 보간된 오른손 item의 로컬 `[0,6,0]`이다. 실제 staff JSON의 raw `(8,12,8)`을
  중앙 정렬하고 translation `[0,2,0]`, native handed 변환, inner Ry180을 적용해도 같은 +Y
  목표가 된다. ready는 기존 접촉 자세를 유지하며 start/end의 소환·놓기는 이 양손 고정 대상이 아니다.
  생성기 검사는 40Hz 모든 sample의 **정적 저작 접촉**을 확인한다. 부모의 실제 sent-globalState
  40Hz 검사 및 화면 보간 인수와 구분하며, 이 변경만으로 엔진/픽셀 접촉 통과를 주장하지 않는다.
- start는 중립 → 모음 → materialize → guard, end는 guard → 내림 → 중립이다.
  전신을 teleport하거나 entity yaw/velocity를 바꾸지 않는다.

## 4. Solar — 소환, 정확한 shot hold, 반동과 퇴장

- 낮은 draw에서 총을 들어 준비 조준으로 연결한다. 오른팔·팔꿈치로 쏘고 왼팔은 낮게 guard한다.
- shot clip은 0/.05/.10초에 **같은 조준 자세**를 명시한다. 발사 전에 반동을 시작하지 않는다.
  .15초에 팔/팔꿈치/흉곽이 뒤로 밀리며 총구가 들리고, .20초 후 감쇠하여 .35초에 ready로 돌아온다.
- 현재 Golden Gun 모델의 barrel은 로컬 +Z다. authoring에서 오른손 item의 bind Rx(-90)와
  흉곽/팔 체인을 역산하여 barrel을 저작 전방 -Z로 향하게 했다. MC/BetterModel 축 변환 검증은
  아직 별도이며 위 엔진 contact 실패와 같은 이유로 실제 방향 인수로 단정하지 않는다.
- start/end의 right item scale은 `.001 → 1` / `1 → .001`이다. **메시 축소 연출**이지 알파·
  표면 분해 셰이더가 아니다. end .25초 표식에서 부모가 시각 장비 override를 제거해야 한다.
  ready/attack에는 unit scale 끝점을 명시해 이전 축소가 남지 않도록 했다.
- 1인칭 HUD 소환/총구/탄수/반동/소멸은 부모 소유다. 이 파일들이 HUD를 구현했다고 표시하지 않는다.

## 5. Void — 매 서버틱 모델 단계와 IK

부모 bow generator가 만들 네 상태는 rest3.27 / partial5.00 / partial6.75 / full8.24다.
H19B의 왼손 JSON Y+90 → 실제 effective Y−90, display translation `[0,2,0]`을 전제로 한
**저작 좌표 계약**이다. nock offset은 bone-local 모델 단위이며 블록 단위가 아니다.

| clip time | accepted elapsed tick | nock local `[x,y,z]` | 저작 world item pitch |
|---|---:|---|---:|
| .00 | 1 | `[0,2,3.27]` | −30° |
| .05 | 2 | `[0,2,3.27]` | −20° |
| .10 | 3 | `[0,2,3.27]` | −12° |
| .15 | 4 | `[0,2,5.00]` | −6° |
| .20 | 5 | `[0,2,6.75]` | −2° |
| .25 | 6 | `[0,2,8.24]` | 0° |
| .30 | **7 release** | `[0,2,8.24]` | 0° |

각 key의 오른손은 `left wrist + Rx(itemPitch) × nockOffset`을 목표로 IK를 다시 푼다.
.25/.30초는 같은 완전 당김 포즈로 고정하고, .35초에는 오른손이 시위에서 떨어져 후행한다.
.90초에 H19의 낮은 ready로 복귀한다. parent는 elapsed4/5/6에 각 partial/full 모델을 넣고
elapsed7에 nocked arrow를 제거해야 한다. geometry만 바꾸고 같은 full draw 손 위치를 일찍 쓰지 않는다.

`h_ph_head`, `pra_right_arm`, `pla_left_arm`의 직접 부모는 모두 `pc_chest`다.
활 item은 팔/전완의 자손이다. 부모 upper-body aim modifier는 이 가슴 체인에 적용하여
머리/두 팔/활을 함께 기울여야 하며 head만 별도로 두 번 pitch하지 않는다.
이 작업은 계층을 바꾸지 않았고 aim modifier 자체를 구현하지 않았다.

정적 Python FK의 seven-stage wrist–nock 오차는 각각 **0.000001 모델 단위 미만**이다.
이 수치를 픽셀/엔진/네트워크 접촉으로 번역하지 않는다. 부모 보고의 실제1.59블록 차이는
별도 bind/축/position API 감사와 실제 BonePosition 검사로 해결해야 하는 미완료 항목이다.
모델 상태 사이의 연속 프레임 접촉도 단계식 geometry와 엔진 보간 때문에 별도 검사 대상이다.

## 6. 일반 능력과 네 방향 회피

수류탄은 어깨를 뒤로 모은 뒤 던지는 전신 동작, Arc 근접은 짧은 chamber–jab–guard 복귀다.
Solar 칼은 높은 팔, Void 연막은 낮은 underhand를 쓰며 같은 이름/색만 바꾼 복제가 아니다.
`h15_throw`는 Solar와 같은 범용 high-cast 모션을 별도 논리 이름으로 제공한다.
부모가 `grenade`/`melee`/`melee_solar`/`melee_void` 또는 완전한 `h15_` 이름을 요청할 수 있다.
`h20_*`는 이 팩의 논리 prefix가 아니며 기존 loader의 h15-only 계약과 호환되지 않는다.

네 roll은 기존 ±360°와 방향 우선 규칙을 유지한다. 어깨 선행·전완 guard·무릎 말기와
발 디딤을 재저작하고, 지정 접촉 key에서 skull이 저작 바닥의 최저점이 되지 않도록 guard IK를 썼다.
평평한 skin cube 바닥에만 맞춘 visual root Y이며 root X/Z 이동은 항상0이다.
회피에는 bounded100Hz, 나머지 신규 clip에는40Hz의 Y 보정 key를 넣어 중간 ground clipping을 줄인다.
이것은 바닥 높이를 실시간 추적하는 기능이 아니다. 계단/경사/방어구/망토 관통은 미검증이다.

## 8. 재생성과 검증

```sh
rtk proxy python3 -B scripts/build_hunter_animation_h20.py
rtk proxy python3 -B scripts/build_hunter_animation_h20.py --verify
# H20 아티스트 편집을 보존하고 클립만 추출
rtk proxy python3 -B scripts/build_hunter_animation_h20.py --from-art
```

기본 명령은 H20 아트/팩만 쓴다. H15/H19 생성기나 `main()`을 실행하지 않고 순수 helper만 import한다.
bytecode cache 생성을 끄므로 공유 scripts 디렉터리에 `__pycache__`를 쓰지 않는다.
`--verify`는 쓰지 않는다. `--from-art`는 아트를 덮어쓰지 않으며 모든 계약 검사를 통과한 팩만 쓴다.

실행한 것은 Python 정적 검증과 재생성 일치 검사다: 리그/아트 보존,19개 논리 clip,
16 animator bone, UUID/채널 시간 중복 방지, 유한수, bounded key 수와 root Y,
root X/Z=0, 루프 이음새, attack/start/ready 연결, 타이밍 키, 단계별 authoring IK,
지정 roll key의 head clearance를 검사한다.
새 JUnit9개는 번들 리소스 이름/길이/marker/채널/루프/아이템 scale/방향과 Void ready 상속을 검사한다.
**JUnit/Gradle/GameTest는 이 작업자가 실행하지 않았다.**

Blockbench 네이티브 MCP/UI가 이전 단계에서 응답하지 않았다는 작업 조건을 존중하여
결정적 JSON 저작 경로를 사용했다. 사용자 프로젝트를 열거나 수정하지 않았고 네이티브 preview,
실제 게임 프레임버퍼, 다인 관찰자, 1인칭/GCB, 저속 TPS 인수 완료를 주장하지 않는다.
실제 BetterModel contact 실패를 해결한 후 부모의 통합 테스트/네이티브 렌더 인수가 필요하다.

## 9. 부모 통합 최종 검증 (S7)

위의 미실행/미완료 표현은 하위 작업자 작성 당시의 경계다. 이후 부모가 실제 통합했다.
잘못된 `worldPosition()` 진단과 native display Ry180 누락을 고쳤고, actual sent snapshot에서
전단계/pitch±30·viewyaw/bodyyaw차이를 검사했다. held/draw/release최대gap0.002283블록,
첫 ready→reach0.03185블록을 별도 transition 경계로 검사한다. Arc는40Hz 중간IK 재저작 후
최대0.006756블록이다. 소유 player limb만 server-clock/local pose sampling을 사용한다.
