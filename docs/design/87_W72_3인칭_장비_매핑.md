# W72 — 3인칭 장비 매핑의 지속성

## 관측과 재현을 구분

W71 Gate1의 기존 공허 활 테스트는 실제 BetterModel 왼손 display에서 `shadow_bow_h28_drawn` 대신 원래 보조 손 diamond를 관측했다. 이후 같은 소스 두 번 통과했다는 사실만으로 원인 해결을 주장하지 않는다.

이번에는 `PlayerAnimations.superItem` 이후 BetterModel의 실제 `TrackerUpdateAction.itemMapping()`을 실행해 외형 override가 유지되는지 검증한다. 이 동기 호출은 장비 재매핑 시 덮어쓰기 경로의 결정적 재현이며, 기록하지 못한 W71 비동기 스케줄 순서를 그대로 재현했다는 뜻은 아니다.

기존 코드에서 새4GT가 모두 실제 native display의 diamond/stick 복귀로 실패했고 기존564GT는 통과했다([red](../qa/2026-10-24/w72/red-1.log)). 단순히 저장 변수를 volatile로 바꾸거나 매틱 다시 씌워 해결한 것으로 간주하지 않는다.

## 정확한 dependency와 수정 위치

[3.5.1 bytecode 근거](../../art/weapons/w72/references/mapper-source.md). 로컬 읽기용 BetterModel checkout은3.6.0이므로 전체를3.5.1소스로 간주하지 않는다. API/Fabric3.5.1 cached JAR의 메서드와 line table을 따로 대조했다.

기본 왼손 mapper는 실제 offhand를 읽는다. `TrackerUpdateAction.itemStack`은 출력만 바꾸고 mapper는 바꾸지 않는다. `completeContext().thenAccept`의 bone context 갱신이나 패킷 기반 장비 재매핑은 기본 mapper 결과로 출력이 바뀔 수 있다. 시계 mixin이 이 별도 future/장비 경로를 차단하지 않는다.

지속 mapper wrapper만 설치해도 **mapper 평가와 실제 기록 사이**의 오래된 결과를 취소할 수 없다.3.5.1은 mapper를 먼저 평가하고, 나중에 `itemLock` 안에서 native display에 기록하기 때문이다.

- 새 `LimbEquipment`는 immutable 선택 record 하나를 volatile로 게시한다. 양손 선택이 서로 다른 mutable 필드 조합으로 읽히지 않는다. 실제 두 display가 동시 갱신된다는 보장은 아니다.
- 새 `BetterModelEquipmentMixin`은 실제 `RenderedBone.itemStack` commit에서 **동일한 native itemLock**을 잡고 현재 선택을 다시 읽는다. 강제 prop/오른손 AIR 또는 현재 context의 원래 mapper를 적용한다.
- 원래 mapper/hand transform은 교체하지 않는다. Supplier는 선택 상태만 읽고 player/tracker를 캡처하거나 다른 lock을 잡지 않는다.
- 첫 binding 이전부터 계산 중이던 기록과도 순서를 정하려고 비소유 bone도 이 commit의 기존 native lock을 먼저 통과한다. 비소유 출력/mapper는 바꾸지 않는다. 성능이 같다고 측정한 것은 아니다.
- EMPTY/close 전에 NONE을 게시하고 양손을 동기 갱신한다. guard는 bone 수명 동안 남아 있어 나중에 들어온 옛 prop 결과도 현재 실제 손으로 바뀐다. 별도 전역 registry/보정 scheduler는 없다.
- 기존 tick의 live 장비 refresh는 유지하지만 forced prop를 직접 반복 기록하지 않는다. 매핑이 임의 시점에 갱신되어도 commit 자체에서 선택을 지키는 것이 수정의 핵심이다.
- `getOrCreate`가 반환한 기존 외부 tracker에는 생성 initializer가 호출되지 않아 policy가 바인딩되지 않는다. 새6번째GT로 이 경로의 무단 인수를 재현한 후, 실제 생성/binding이 확인된 경우에만 clock/ACTIVE를 소유하도록 고쳤다. 외부 tracker는 닫지 않고 외형 시작을 거절한다.

권한 범위는 우리 hunter/sword limb의 두 장비 bone이다. 소유 bone에서 direct item/enchant 출력도 현재 선택이 우선한다. 제3자 custom mapper/predicate/mixin의 모든 lock 조합이나 직접 `ModelDisplay.item`으로 우회한 쓰기까지 검증한 것은 아니다.

## 불변 조건

- 오른손 prop은 해당 손만 대체하며 왼손은 현재 inventory의 live mapping이다.
- 왼손 활은 활을 왼손에 표시하고 오른손을 비운다. 양손 동작은 하나의 장비 선택 상태로 취급한다.
- prop 교체, 입력 ItemStack의 후속 변경, 실제 손 아이템 변경, EMPTY 복구, stop, tracker 교체를 구분한다.
- override 해제는 시전 때 복사한 inventory가 아니라 **현재 손 아이템**을 복원한다. 실제 inventory/count/components를 수정하지 않는다.
- 닫힌 이전 tracker의 갱신은 새 tracker의 장비를 덮어쓰거나 옛 prop을 부활시키지 않는다.
- 외부/비소유 BetterModel tracker의 기본 매핑은 바꾸지 않는다. 별도 보정 스케줄러나 매틱 재시도로 증상을 숨기지 않는다.

## 검증 경계

GameTest는 실제 native ItemDisplay의 ItemStack을 읽는다. 요청한 Playback 값만 비교하지 않는다. 기존 공허 활·검·궁극기·장전·HUD 회귀를 유지한다. 서버 장비 상태/패킷과 실제 Minecraft 클라이언트 픽셀/조작/청취를 구분한다. W62의 승인된 격리 진단 이후 새 native client는 실행하지 않는다.

전체 무기/HUD 목표는 active다. [QA](../qa/2026-10-24/w72/README.md)에 재현 결과·정확한 dependency 근거·수정 및 남은 경계를 남긴다.
