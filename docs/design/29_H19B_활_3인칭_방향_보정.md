# H19B — 활 3인칭 좌우 손 변환 보정

## S1. 재현과 원인 조사 (2026-10-22)

사용자 제보: H19 활이 반대로 들린다. H19의 정적 FK는 손/시위/화살의 위치를 계산했지만 Minecraft의 handed display 변환을 생략했다. JSON 숫자가 기대값인지 확인하는 테스트도 이 런타임 차이를 잡지 못했다.

실제26.3 merged JAR의 `net.minecraft.client.resources.model.cuboid.ItemTransform.apply(boolean, PoseStack.Pose)` 바이트코드를 확인했다. 왼손은 translation X와 rotation Y/Z를 반전한다. `ItemStackRenderState.LayerRenderState.applyTransform`은 `displayContext.leftHand()`를 넘긴다. 따라서 왼손 JSON Y−90은 실제 Y+90이 되어, 의도한 화살 local−X→shot−Z와 시위+nock→archer+Z가 뒤집힌다.

실제 MC `ItemTransform.apply`를 호출하는 새 회귀 테스트를 먼저 추가했다. 기존 리소스에서 `string must face the archer (+Z)`가 실패했다. 실패 XML/로그와 bytecode는 [H19B QA](../qa/2026-10-22/h19b/)에 저장했다. 이 단계에서는 아직 화면 인수 완료를 주장하지 않는다.

수정 범위: H19 rest/drawn의 명시적인 왼손/오른손 third-person display, 재생성 가능한 Blockbench/아이템 파일, handed 변환을 포함한 회귀 검사. 기존 아티스트 설치 모델·H15·gameplay 타이밍·다른 궁극기 clip은 변경하지 않는다.

## S2. 변환 보정과 추가 내보내기 결함

왼손 JSON `[0,+90,0]`, 오른손 `[0,-90,0]`로 두 손의 유효 회전을 모두 Y−90으로 맞췄다. 두 상태 모두 translation `[0,2,0]`과 기존 grip/scale을 유지한다. BetterModel API→LEFT_ITEM mapper→THIRD_PERSON_LEFT_HAND 경로도 독립 소스/bytecode 감사로 확인했으며 중간에 별도의180도 보정은 없었다.

첫 수정 뒤 GameTest104/JUnit60과 실제 측면 반전 비교는 통과했다. 그러나 isolated drawn display에서는 직선 시위가 남고 새 화살이 보이지 않았다. 이를 성공 증거로 사용하지 않고 `pregeometry/`에 보존했다. 추가 독립 감사에서 두 결함을 확인했다.

- BB `spectral_bowstring`은 element196, vanilla JSON에서는201이다. 같은 배열 index를 지우던 코드가 runtime wisp를 지우고 시위를 남겼다. 이름으로 찾은 BB 시위의 고유 bounds로 runtime 요소를 대응시킨다.
- BB 픽셀 UV `[195,36,221,124]`를 vanilla에 그대로 복사했다. 256×128 atlas의 정규화 좌표는 `[12.1875,4.5,13.8125,15.5]`이다. 이미 올바르게 export된 runtime 시위의 faces를 복사한다. BB용 픽셀 UV는 그대로 유지한다.

실제 MC26.3 parser는 모든206개 elements와 legacy `axis/angle` 회전을 읽는다. `groups`는 렌더링 필터가 아니며 `texture_size`로 UV를 자동 정규화하지 않는다. 내보내기 group metadata/BB outliner도 새 시위·화살 다섯 요소를 포함하도록 갱신했다.

기존 직선 시위 제거·모든 비시위 요소 보존·추가 faces의 정규화 UV 계약을 강화했다. 수정 전 새 assertion이 실패하는 XML을 보존한 뒤 generator를 수정했다. 큐브 수만 맞는 검사를 인수 기준으로 사용하지 않는다.
