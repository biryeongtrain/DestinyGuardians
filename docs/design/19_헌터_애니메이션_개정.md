### 추가 조사: 오프라인 스킨 색 전환의 원인

BetterModel Fabric/core3.5.1의 실제 JAR를 `javap -p -c`로 읽고 소스 체크아웃
`7dc7eed785854f81a3826e7a2e188a53ce5215d7`과 대조했다.
`ModelProfileImpl`은 GameProfile에 인증 `textures`가 없으면 `ModelProfileSkin.EMPTY`를 반환한다.
`SkinManagerImpl.complete`는 스킨 URI가 null이면 자체 `fallback_skin.png`를 사용한다.
따라서 클라이언트가 UUID로 고른 바닐라 기본 스킨과 다르다. H15 리그를 잘못 복사해서 생긴 현상은 아니다.

지원 API인 `CreatePlayerSkinEvent#setModelProfile` 또는
`ModelRenderer#getOrCreate(entity, ModelProfile, modifier, callback)`는 인증 GameProfile을
변경하지 않고 별도 시각 프로필을 제공할 수 있다. 다만 스킨 로더는 HTTP(S) URI를 읽으며,
공개 API에서 PNG/BufferedImage 기반 폴백 생성자·setter는 찾지 못했다.
오프라인 기본 스킨 일치는 의존성의 폴백 개선/이미지 로딩 API가 필요하다.
UUID 추측 매핑·인증 속성 변경·로컬 스킨 HTTP 서버는 추가하지 않았다. 이 문제는 **미해결**이다.

## 2. 1단계: 스킨 리그와 아티스트 설치 파일 보존

설치 이름은 `guardian_hunter_h15`, 대상은
`config/bettermodel/players/guardian_hunter_h15.bbmodel`이다.
기존 `guardian_hunter.bbmodel`은 읽거나 덮어쓰거나 삭제하지 않는다.
H15 대상도 한 번 생기면 아티스트 소유다. 존재 검사에 NOFOLLOW_LINKS를 적용하며,
쓰기에는 CREATE_NEW를 사용해 검사 직후 생긴 파일·심볼릭 링크도 덮어쓰지 않는다.

BetterModel이 제공하는 현재 `/steve.bbmodel`을 깊은 복사하고, H15 애니메이터를 뼈 이름으로
찾아 현재 템플릿 UUID에 다시 매핑한다. groups, elements, outliner, textures, UV,
스킨·방어구·머리·망토·아이템 뼈와 기존 roll은 그대로 남긴다.
필수 뼈가 없으면 잘못된 리그를 설치하지 않고 경고 후 기존 모델로 폴백한다.

선택 순서는 설정 가능한 `PlayerAnimations.limb`(기본 H15) → `guardian_hunter` →
`PlayerAnimations.fallbackLimb`(기본 steve)이다. 각 모델에서 실제 지원하는 클립만 선택한다.
구형 모델의 단일 roll은 방향 회피의 시각 폴백이며, 공격 원샷이 없는 구형 궁극기 모델은
기존 준비 자세를 유지하고 `superAttack`이 false를 반환한다. 공격을 roll로 대체하지 않는다.
BetterModel이 없을 때를 위해 modifier 클래스 초기화도 지연한다.

이미 설치한 H15 파일은 에셋 변경만으로 갱신되지 않는다. 아티스트가 편집한 설치 파일을
유지할지, 별도 백업 후 새 파일을 설치할지는 배포 담당자가 결정한다. 이 작업에서는
실제 서버 config 파일을 수정하지 않았다.

## 3. 2단계: 방향 회피와 접촉 타임라인

| 입력 | 클립 | 몸 회전 |
| --- | --- | --- |
| 앞으로 / 입력 없음 | h15_roll_forward | root X: 0 → -360° |
| 뒤로 | h15_roll_back | root X: 0 → +360° |
| 왼쪽 | h15_roll_left | root Z: 0 → +360° |
| 오른쪽 | h15_roll_right | root Z: 0 → -360° |

네 클립 모두 0.70초, 9개 전신 키 포즈다.

1. 0–0.10초: 작은 반동, 무릎 굽힘, 팔을 모으는 예비 동작.
2. 0.10–0.40초: 어깨 접촉, 허리·가슴 말기, 무릎/팔꿈치 접기, 한 바퀴 회전.
3. 0.40–0.60초: 발 디딤, 몸 펴기, 망토의 후행 동작.
4. 0.60–0.70초: 중립 자세 정착. 완료 후 궁극기 준비 루프 또는 바닐라 플레이어로 복귀.

뼈 좌표에서 접촉 키의 최저 skin cube가 바닥에 맞도록 루트 Y를 계산했다.
수평 루트 위치는 0이며 이동은 기존 물리만 담당한다. 큰 회전의 root는 linear,
관절은 catmullrom이며 quaternion_interpolation은 false다.

`HunterDodge`의 변경은 시각 클립 선택 한 줄이다. `Motion.inputDirection`, 정규화된
대각선 속도, 기본 speed 1.15, lift 0.18, 기본 invulnerable_ticks 6, 낙하 거리 초기화,
효과음·먼지·도박꾼 근접 재충전은 유지한다. 플레이어 yaw/pitch를 변경하지 않는다.
서로 반대 입력은 상쇄한다. 대각선은 물리상 정확한 대각선이며 시각 클립은 앞/뒤를 우선한다.
바닥 접촉 계산은 키 포즈의 저작 보조이며, 키 사이 보간과 계단/경사 접촉은 실제 게임에서 확인해야 한다.

## 4. 3단계: 준비 자세와 공격 원샷

| 속성 | 준비 루프 | 원샷 | 길이 / 강조 시점 |
| --- | --- | --- | --- |
| Arc | h15_super_arc | h15_super_arc_attack | 준비 1.6초, 공격 0.30초; 0.05초 예비 회전, 0.10초 교차 스윕, 0.15초 후속 호 |
| Solar | h15_super_solar | h15_super_solar_attack | 준비 2.0초, 공격 0.40초; 0.05초 조준 정착, 0.10초 총구·팔·상체 반동 |
| Void | h15_super_void | h15_super_void_attack | 준비 2.4초, 공격 0.55초; 0.08–0.16초 당김, 0.21초 손을 놓고 0.30초 후행 |

준비 루프는 비대칭 하체 지지, 속성별 팔/장비 자세, 작은 호흡과 망토 움직임을 가진다.
모든 루프의 처음/마지막 값은 같고, 공격 처음/끝은 해당 준비 루프의 기준 자세와 같다.
기본 준비 루프는 priority 0, 원샷은 priority 20으로 같은 tracker 위에 재생한다.
재공격은 이전 원샷만 취소하고 새 원샷으로 교체한다. 준비 루프와 시각 장비는 유지한다.

이 타임라인은 시각 연출이며 타격 판정, 탄 소모, 화살 발사 시각을 지연하지 않는다.

## 5. 4단계: 부모 통합 API와 종료 계약

모든 공개 진입점은 서버 메인 스레드에서 호출한다.

```java
// 궁극기 시작: 기존 호출과 호환
PlayerAnimations.loop(player, "super_" + element.getSerializedName());
PlayerAnimations.superItem(player, SuperVisuals.item(element));

// primary의 쿨타임/탄 수 등 검사를 통과한 경우에만 호출
boolean visualStarted = PlayerAnimations.superAttack(player, element);
// false는 시각 클립 미지원이며 게임플레이 실패가 아니다.

// 매 서버 틱: 부모가 AbilityService에 통합
PlayerAnimations.tick(server);

// 자연 종료 / 마지막 Solar 탄 / Void 발사 후 세션 종료
PlayerAnimations.finishSuper(player);

// 사망 / 로그아웃 / 클래스 변경 / 강제 취소
PlayerAnimations.stop(player);
```

`superAttack(ServerPlayer, Element)`는 boolean이다. 해당 속성의 활성 준비 루프가 있어야 한다.
KINETIC, 다른 속성, 지원하지 않는 클립, 이미 종료 중인 상태는 false다.

`finishSuper(ServerPlayer)`는 void다. 진행 중인 원샷이 있으면 closingAfterRun을 표시하고
준비 루프를 즉시 중단한다. 그 원샷과 시각 장비만 회복 동작까지 남기며, 원샷 완료 시
tracker와 장비 override를 제거한다. 원샷이 없으면 즉시 정리한다. 반복 호출은 안전하다.
게임플레이 SuperSession 수명을 연장하지 않는다. 부모 Session.end가 이 함수를 호출하고,
AbilityService.cleanup의 명시적 stop은 그대로 두면 즉시 취소가 우선한다.

BetterModel 완료 콜백은 뼈마다, 스케줄러 스레드에서 호출될 수 있다.
콜백에서는 해당 Run의 AtomicBoolean만 갱신한다. ACTIVE, tracker, 장비에는 접근하지 않는다.
tick은 현재 Run만 검사하므로 중단한 공격의 늦거나 중복된 콜백이 새 공격이나 새 세션을
닫을 수 없다. 클립 전체 길이 + 시작 보간 1틱까지 기다려 짧은 뼈의 조기 콜백도 제한한다.
콜백이 오지 않더라도 추가 6틱 후 원샷을 정리한다. 보통 완료 전환은 다음 정상 서버 틱에서
처리되며, tick 호출 누락 시 자동 복귀가 진행되지 않으므로 통합이 필수다.

owner가 죽음/제거/연결 종료/차원 변경 상태이거나 tracker가 닫혔으면 다음 tick에 정리한다.
기존 GCB 카메라 전환 훅은 refreshOwnerVisibility를 그대로 쓴다.

장비 override는 ItemStack.copy로 만든 시각 스냅샷이며 실제 인벤토리를 바꾸지 않는다.
준비/공격 중에는 동일한 변환 스택을 재사용하고 틱마다 유지해 장비 매핑 갱신에도 복구한다.
superItem(player, ItemStack.EMPTY)는 override를 비우고 현재 손 장비 매핑으로 복구한다.
stop/최종 원샷 완료에서는 live itemMapping을 복구한 뒤 tracker를 닫아 바닐라 스킨·장비·idle이
보이게 한다. 궁극기 중 일반 공격 완료는 준비 idle로 돌아간다.

## 6. 5단계: 소스 저작과 추출

최초 생성에 사용한 BetterModel 템플릿은 워크스페이스의
`work/bm/core/src/main/resources/steve.bbmodel`이다.

```sh
rtk proxy sh -c 'python3 scripts/build_hunter_animation_h15.py --template /absolute/path/to/steve.bbmodel'
rtk proxy sh -c 'python3 scripts/build_hunter_animation_h15.py --from-art'
```

첫 명령은 H15 아트와 패키지 클립을 재생성하므로 아티스트 편집 후에는 실행하지 않는다.
Blockbench에서 H15 아트 파일을 편집한 다음에는 두 번째 명령으로 클립만 추출한다.
런타임은 클립의 animator.name으로 현재 템플릿 UUID를 찾는다. 전용 h15_ 이름을 유지하고
필수 스킨 뼈 이름을 변경하지 않는다.

Blockbench MCP는 사용 가능했고 활성 사용자 프로젝트와 탭 목록을 읽기 전용으로 확인했다.
전용 H15 프로젝트를 로드하고 이전 탭으로 복귀하는 원자 호출을 요청했으나 응답이 반환되지
않아 중단했다. 따라서 MCP 편집·내보내기·시각 미리보기 완료를 주장하지 않는다.
사용자/다른 에이전트 탭을 대상으로 수정·저장·닫기를 수행하지 않았다.
추후 MCP 작업은 매 원자 호출 시작에 H15 프로젝트 UUID를 선택하고 다른 작업자의 현재
프로젝트에 의존하지 않아야 한다.

## 7. 검증 이력: 실제 실행과 미실행 구분

실제 실행한 읽기 전용 검증:

- 10개 H15 클립 존재와 아트/패키지 클립의 완전 일치.
- 원본 BetterModel 템플릿과 meta/groups/elements/outliner/textures 완전 일치.
- 기존 roll 보존, 애니메이션·키 UUID 중복 없음, 모든 키 값 유한수.
- 각 클립의 16개 뼈, 채널 시작 0/끝 length, 중복 시간 없음.
- 4방향 root의 정확한 ±360° 회전, root yaw 0, 수평 root 이동 0.
- 세 준비 루프의 이음새와 세 공격의 처음/마지막 준비 자세 일치.
- 소유 Java 파일의 git diff --check 통과.
- 실제 캐시된 BetterModel 3.5.1 JAR를 javap로 읽어 priority builder, BlueprintAnimation.length,
  itemMapping, BoneName.rawName API를 확인했다.

추가한 JUnit 6개는 UUID 재매핑/리그 보존, 설치 파일 보존, 불완전 템플릿 거부,
지연·중복 콜백 격리, 누락 콜백 유예, 입력 방향 선택을 검사한다.
이 작업에서는 Gradle을 실행하지 않아 추가 테스트를 직접 실행하지 않았다.

부모가 등록할 GameTest 클래스는
`kim.biryeong.destiny.test.HunterAnimationH15GameTests`다. 등록 파일은 수정하지 않았다.
5개 테스트는 실제 H15 limb 로딩을 기다린 뒤 정상 서버 틱으로 다음을 검사한다.

1. Void 발사 후 게임 세션이 끝나도 release가 남고 회복 후 정리된다.
