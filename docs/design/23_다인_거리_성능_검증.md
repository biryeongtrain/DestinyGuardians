## S2 — 계측과 실제 2인 접속

- 옵트인 `-Ddestiny.qa=true`에서만 `destiny qa`를 등록한다. 기본 실행에는 QA 부하/측정 작업이 없다.
- `scene <player>`는 실제 HunterVfx 닻을 고정 위치에 유지한다. `load [player]`는 연결된 최대6명(또는 지정1명)마다 BetterModel4개+선4개를 유지하며2400틱(20TPS에서120초)에 종료한다. 피해·인벤토리·쿨타임은 건드리지 않는다.
- `sample <label> <5..60초>`는 완료된 서버 틱의 나노초 링을 매 틱 읽어 원시 자료와 벽시계 진행률을 저장한다. 타깃20TPS와 측정값은 구분한다.
- 읽기 전용 VFX 스냅샷은 선택된 실제 viewer UUID를 노출하며 spawn/despawn 자체를 바꾸지 않는다.
- 원본 Vision 프로젝트는 수정하지 않았다. 분리 스냅샷 생성기로 FPS 카운터와 로드된 엔티티 목록만 `/state`에 추가했다. 렌더링/입력 동작은 기존 비전 클라이언트 그대로다.
- `H16Caster`/`H16Observer`, HTTP8102/8103, 독립 실행 폴더로 실제 동시 접속. 두 클라이언트 모두 필수 팩을 수신했고 실제 PNG에서 HUD/모델이 표시됐다.
- 15:32:59 빌드에서 GameTest80/80 통과(신규9개), 기존 JUnit28개 포함 build 성공. 신규 테스트는 전역24+24/소유자4+4, 소유자 격리·만료·정리·96블록 길이/대상 반경 경계다.

## S3 — 거리와 관찰자

- 닻 중심 `(206.5,-60,0.5)`, 관찰자 같은 Y/Z에서 X만 변경. 47.99/48.00에서 실제 클라이언트에 닻 item_display3개가 존재하고 서버 viewer에 포함됐다.
- 48.01/64.00에서 해당3개가 제거되고 서버 viewer에서도 제외됐다. 가까운 위치로 복귀하면 같은 ID3개가 다시 수신되고 실제 PNG에 닻이 재표시됐다.
- Viewer 갱신 주기는5틱이며 본 검증은 이동 후 안정 상태다. 모든 순간에 지연0으로 전환한다는 뜻은 아니다. 48블록의 작은 화면 픽셀보다 엔티티/서버 스냅샷이 정밀 경계의 주 증거다.
- Solar 시전자와 Arc 관찰자가 동시에 궁극기를 발동/공격했다. 관찰자는 상대의 3인칭 총·준비/발사 포즈를 보며, 본인의 1인칭 지팡이는 별도로 표시됐다.
- 시전자 본인 1인칭 limb 숨김과 QA 3인칭 표시 전환에도 관찰자 모델은 유지됐다. 실제 GCB 전송이 아닌 명시적 QA override다.
- 오프라인 계정의 BetterModel fallback 스킨 색 전환은 H15와 동일하게 남아 있다.

## S4 — 조명·선 거리·늦은 접속

- 같은 위치/카메라/HUD/밝기 옵션에서 낮·자정·완전히 막힌 돌 방을 촬영했다. 닻의 보라색 곡선은 환경이 어두워져도 보인다. 주변 벽/플레이어를 밝히는 동적 광원은 아니다.
- 차폐 공간에서 실제 Shadowshot을 발사했고, 명중 대상의 윤곽과 공허 연결선이 보였다. 자연 동굴 생성/모든 조도·모든 속성의 전수 시험이 아니라 통제된 차폐 공간이다.
- JVM2에서 scene을 먼저 시작한 뒤 관찰자를 실제 재접속시켰다. 기존 위치의 닻을 수신하고 서버 viewer 목록에도 추가됐다.
- 다른 소유자의 선이 결과를 가리지 않도록 QA load의 대상1명 옵션을 추가했다. 한 소유자의4개 선은32블록에서 보이고64블록에서 화면에서 사라지며 가까이 복귀하면 재표시됐다.
- **중요한 구분:** Polymer 선은64블록에서도 클라이언트 엔티티 목록에4개가 남는다. `viewRange=0.75`는 클라이언트 렌더링 거리이며 BetterModel의48블록 서버 viewer 필터와 다르다. 먼 관찰자에 대한 패킷 비용0을 보장하지 않는다.

## S5 — 계측 검토에서 발견한 문제와 수정

- 초기 세 창(기준/부하/복구)과 JVM2 예열 부하 창의 FPS/패킷 원시 자료는 보존한다.
- 검토 결과 Fabric의 `END_SERVER_TICK`은 vanilla `tickServer` TAIL에서 실행되어 바닐라 나노초 링의 기록 **이후**였다. 따라서 바닐라 MSPT는 `AbilityService.tick`/VFX 갱신과 QA fixture 생성 비용을 직접 포함하지 않는다. 이를 전체 VFX CPU 비용으로 해석하지 않는다.
- 새 옵트인 `WrapMethod(tickServer)` 타이머로 원래 메서드 호출 전체(주입된 END 콜백 포함)를 측정한다. 바닐라 링과 `whole_tick_nanos`를 분리해 저장한다. 외부 대기·BetterModel 비동기 작업·클라이언트 렌더링은 별도다.
- 틱 진행률도 명령 실행 시작 경계가 아닌600회 START 관측 사이599개 구간으로 계산하는 값을 추가했다. 지연을 타깃20TPS 값으로 대체하지 않는다.
- 초기 JFR 시작 직후237/88ms 스파이크는 원시 자료에 남긴다. 새 JVM3에서는 기록 시작/월드 준비를 먼저 마치고 예열 뒤 재측정한다.
- HTTP 측정은 포트별 오류와 중간 결과를 저장하도록 보강했다. 한 클라이언트의 타임아웃 때문에 다른 클라이언트와 기존 표본이 모두 사라지지 않는다.
- JVM1의 추가 옵션 없음→JVM2의1인 부하/차원 보호→JVM3의 전체 호출 타이머 순으로 QA만 변경했다. 게임플레이·모델·텍스처·셰이더는 바꾸지 않았다. 매번 서버 중지 후 빌드/새 JVM으로 실행했다.
- JFR 재시작 시 Minecraft 요약의 `durationMs`에 이전 구간의 장기 이벤트가 섞인 것을 확인했다. 송신/수신 패킷 이벤트 자체의 타임스탬프를 실제30초 클라이언트 표본 창으로 필터링하여 비율을 계산한다. payload 바이트이지 TCP 전송 바이트가 아니다.

## S7 — 종료·회귀·인계

- 실제 시전자에게4닻+4선을 만든 뒤 시전자를 멀리 이동시켰다. 효과는 유지됐다. 해당 자체 클라이언트의 접속을 종료하자 관찰자 화면에서 제거되고 서버 풀도0/0으로 정리됐다.
- QA 몹/드롭·임시 돌 방을 제거했고 개발 QA 바닥만 남겼다. 두 QA 플레이어 스폰·Arc·first 신호, 낮/맑음, active0/beam0으로 복구했다.
- 자신의 서버3개 모두 정상 종료, 자신의 비전 프로세스만 SIGTERM했다. 포트25565/8102/8103 비점유, 원본 비전 저장소 clean과 options SHA256 동일 확인. 원본 options를 변경했다가 덮어쓴 방식이 아니라 처음부터 분리했다.
- 최종 release 재빌드 **GameTest80/80·JUnit28/28**, 실패/오류/스킵0. QA 미활성 기본 실행에서도 회귀 통과, 새 타이머의 활성 경로는 JVM3 실제600+600표본으로 확인했다.
- 본 단계는 게임플레이/아트 수정 없이 옵트인 fixture·정확한 계측·회귀 테스트를 추가했다. 운영 서버에서 QA stop을 쓰면 선택 소유자의 기존 효과도 정리하므로 **동시 실전 플레이가 없는 격리 환경 전용**이다.
- 남은 범위: 인증 스킨/GCB 실제 전송/Vulkan/타 해상도/청음, 실제6인 이상 및 모든 능력 혼합 장기 부하. 일반 총기·탄약·재장전·명사수 회피 재장전(5번)은 착수하지 않았다.
