# H19 카메라 이동 보정 (sidecar)

## 범위와 상태

- 대상: `feat/hunter`, Minecraft 26.3, 서버 전용 Arc/Void 원격 카메라.
- H18 실제 연결에서 forward/sprint Input을 받지만 body가 고정되는 원인을 JAR 바이트코드로 확인하고 최소 보정을 추가했다.
- **빌드, GameTest, 서버/클라이언트 실행은 하지 않았다.** 메인 작업자가 통합 후 실행할 검증이다. 정적 확인을 실제 접속 재검증 성공으로 해석하지 않는다.
- animation/ability/PlayerAnimations, 공용 로그, 빌드 및 등록 파일은 수정하지 않았다. 커밋하지 않았다.

## 원인과 근거

H18 `docs/qa/2026-10-22/h18/vision-v1-camera-input-report.json`의 forward=true 관찰 45개 모두 local body가 `(100.5, -60, 100.5)`, camera ID가 94였다. `vision-v1-server.txt`에서도 서버 body가 같은 위치이고 `active=true`, `rotations=36`, forward/sprint=true였다.

현재 프로젝트의 26.3 merged JAR에 `javap -c -p`를 적용했다. `ServerGamePacketListenerImpl.tickPlayer()`의 순서는 다음과 같다.

| 바이트코드 offset | 처리 |
| --- | --- |
| 1 | `resetPosition()`으로 틱 시작 body를 `firstGoodXYZ`/`lastGoodXYZ`에 저장 |
| 50 | `ServerPlayer.doTick()` 호출; 기존 HEAD/TAIL mixin의 입력·native 물리·낙하 처리가 실제 실행됨 |
| 58, 62, 66 | 앞서 저장한 `firstGoodXYZ`를 읽음 |
| 83 | `player.absSnapTo(firstGoodX, firstGoodY, firstGoodZ, yaw, pitch)`로 좌표 복원 |

즉 native travel이 호출되지 않는 것이 아니라, 연결 wrapper가 그 이동 결과를 즉시 되돌린다. 기존 `nativeSingleTickConsumesKeysFromRestAndCollides`와 낙하 테스트는 `player.doTick()`을 직접 호출하여 이 연결 복원 단계를 통과하지 않았다.

함께 확인한 판정: 서버 Player의 `getMoveSimulationType()`은 `AUTHORITATIVE_SIDE_AND_SERVER`, `isEffectiveAi()`는 서버에서 true이므로 별도 travel 호출이나 제어권 강제 변경이 필요하지 않다.

## 수정

기존 `ServerGamePacketListenerImplMixin`의 `tickPlayer` → `ServerPlayer.doTick()` 호출 **직후**에 주입했다. `SuperCamera.active(player)`인 경우만 native `resetPosition()`을 다시 호출한다.

이 함수는 현재 body의 X/Y/Z를 연결의 `firstGoodXYZ`/`lastGoodXYZ` 여섯 필드에 저장한다. 위치 변경, 이동, 패킷 전송, teleport는 하지 않는 것을 바이트코드로 확인했다. 따라서 뒤따르는 vanilla `absSnapTo()`는 방금 충돌 처리된 위치를 그대로 유지하고 다음 연결 검사 기준도 그 위치가 된다. native 물리는 기존 한 번만 실행된다.

카메라 미소유 연결은 원래 wrapper 동작을 유지한다. 소유 중 위치/ground 패킷 차단과 rotation 수용은 기존 경로를 유지한다. 커스텀 클라이언트 의존성을 추가하지 않았다.

`SuperCamera.java`와 `SuperCameraPlayerMixin.java` 자체의 물리 호출은 변경할 필요가 없어 그대로 두었다.

## 회귀 테스트와 메인 통합 검증

기존 등록된 `SuperCameraGameTests` 안에서만 수정/추가했다.

| 테스트 | 확인할 회귀 |
| --- | --- |
| `nativeSingleTickConsumesKeysFromRestAndCollides` | 기존 전진/좌이동/벽 충돌 테스트를 `connection.tick()` 경로로 강화 |
| `nativeDropDamagesDespiteSpoofedGroundPackets` | 낙하도 연결 wrapper를 거쳐 실제 착지 위치/피해 유지 |
| `connectedSprintAccumulatesExactlyOneNativeStepForArcAndVoid` | 실제 input/rotation handler 경유, vanilla 틱으로 speed 초기화, Arc/Void 각각 8틱 전진/달리기 누적; 매틱 직접 native 한 틱을 실행한 대조 플레이어와 위치 일치하여 이중 이동도 검출 |
| `unownedConnectionRetainsVanillaPositionRewind` | Solar 미소유 상태에서 native travel 뒤 vanilla 연결의 위치 복원이 유지됨 |

등록 변경 제안: **없음**. mixin과 GameTest 클래스 모두 기존 JSON 등록에 존재한다. 새 테스트 메서드는 기존 클래스에 추가했다.

이 sidecar에서 확인한 사항:

- 실제 26.3 `tickPlayer()Z`, `resetPosition()V`, `ServerPlayer.doTick()V` descriptor와 호출 순서.
- `resetPosition()`의 여섯 좌표 필드 저장 및 좌표 getter 이외 호출 부재.
- 기존 mixin/GameTest 클래스 등록 유지.
- `git diff --check` 통과.

메인 작업자가 실행할 사항:

1. 통합 빌드/전체 테스트 및 위 GameTest 4개를 실행하여 mixin 적용과 native 이동량을 확인한다.
2. H18과 동일한 실제 연결의 Arc 100틱 forward/sprint를 다시 실행한다. 서버 authoritative body와 camera/mount가 함께 진행하는지 기록한다.
3. Void에서도 전진·좌우·점프·벽 충돌·낙하와 종료 복원을 확인한다. 지연/청크 경계/다인 시각 검증은 이 정적 작업의 보증 범위가 아니다.

위 내용은 sidecar 단독 단계의 기록이다. 후속 메인 통합 결과는 아래와 같다.

## S4. 메인 통합 결과 (2026-10-22)

- Java25 `runGameTest test build` 성공. 전체104 GameTest/59 JUnit, 실패0. 연결 wrapper를 통과하는 native single-step·Arc/Void 누적·충돌/낙하·unowned 회귀가 포함된다.
- 새 서버/실제 Vision native 입력100틱 forward+sprint로 재현: Arc body Z100.5→139.7826204683161, Void Z100.5→128.55679864354747. 서버 콘솔 body와 클라이언트 상태를 별도 기록했다. 이제 H18의 고정 body 증상은 이 로컬 재현에서 발생하지 않았다.
- 최종 Void camera shoulder는 활 가림 완화를 위해1.15m, Arc는 .45m다. rear3m와 충돌 제한/입력 소유권은 유지했다.
- 실제 테스트는 native 논리 입력이며 OS 키보드/CU가 아니다. 실제 연결에서 벽/낙하·다인·지연을 모두 재현한 것은 아니다. 벽/낙하의 이번 증거는 GameTest다.
- 자세·입력 중립·픽셀·버전 구별과 알려진 저속 TPS 애니메이션 한계는 [H19 QA](../qa/2026-10-22/h19/README.md)에 기록했다.
