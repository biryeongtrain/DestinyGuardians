# H28 — 원본 메시 기반 게임 통합

## S3: 변환 자산 준비 (2026-10-23, 진행 중)

사용자가 원본 메시 기반 수정·진행을 승인했다. 연구-only 단계(설계41) 뒤의 통합 작업이다.
원본 binary/원본 texture 자체는 제외하되 **변환 파생 mesh/RGB/compiled JSON은 로컬 프로젝트에 추가**한다.
원본 권리가 오픈라이선스로 바뀐 것은 아니다. 공개 GitHub/배포/상업적 사용 전 권리 확인이 필요하다.
원본 archive/Blender 재질/리핑 플레이어 애니메이션을 JAR에 포함하는 작업이 아니다.

- 원본 검토 메시의 COPY에만 merge-by-distance1e-6 적용. 원본 Scene/원본 mesh는 보존.
- 지팡이: 9196→2298tri(25% decimate), 끝칼날/링/슬롯/그립 유지. source정점→candidate표면
  일방향 최대편차0.041797 model unit, RMS0.012137(1unit=1/16block).
  전 표면 Hausdorff 거리나 텍스처 오차 측정은 아니다. 같은 재질 Blender 렌더 직접 비교.
- 활: weld 후 독립된 직선시위(15정점/26면) component를 검출·제거. body1384tri는 decimate하지 않음.
  균일비율로 높이24unit, tip 시위축X11.27 근처에 정렬. grip은 raw8 중심 근처.
- base 이미지의 삼각형 평균RGB를 추출한 뒤 geometry/RGB만 `art/mesh/supers/h28/*.mesh.json`에 저장.
  원본 diffuse PNG/DDS·normal/MRC·MATCAP는 번들하지 않는다. UV 픽셀 무늬/원본 shader는 보존되지 않는다.
- 새 java-mesh compiler는 item raw좌표에서 BM 축/단위를 적용하고 양면 primitive로 변환한다.
  지팡이6894 / 활4152 mesh파트. 1삼각형=3파트이며 엔티티/드로콜 수가 아니다.
- 각 leaf primitive에 원래 display context를 적용: vanilla가 display→local matrix 순서로 적용한다.
  왼손미러/yaw와+2Y offset을 변경하지 않는다. 별도 자체 white texel로 외부 BM asset경로 의존성 제거.
- 새 `arc_staff_h28`, `shadow_bow_h28_drawn`, `shadow_bow_h28`를 선택.
  활은 mesh body 공통+기존 H22/H27 시위/화살5큐브, release는1큐브. 이 geometry는 원좌표 그대로다.
- VFX body root만 새 limbX7.35/Y13·3으로 옮긴다. nock16.24/8/8, tip11.27/20·-4/8 불변.
  H26_r2 player clip/궁극기피해/전개11t/공격/후방카메라/HUD 변경 없음.

재생성: Java25의 JAVA_HOME을 설정하고 `rtk proxy python3 scripts/build_super_mesh_h28.py [--verify]`.
Blender/Blockbench나 원본 archive가 없어도 커밋된 중간mesh/RGB로 동일 runtime asset 생성 가능.
source preprocess/집계와 최종 QA는 `docs/qa/2026-10-23/h28/`에 기록한다.

   당김/해제 geometry, source/runtime hashes, 빌더3배파트 검사.
2. 전체 GameTest/JUnit 강제실행. 기존 손접점·조준·실제BM송신·빠른공격 회귀를 새 선택모델로 실행.
3. 실제 서버 생성팩/JAR해시 일치 확인. Vision으로 Arc/Void owner+observer 및 움직임·발사·정리 확인.
4. 새 팩 로그 누락/파싱오류, 정상20TPS 표시, 실화면과 성능 한계 기록. 입력/카메라/fixture 복구.

## S4: 첫 게임 검증 / 재질 피드백

native item codec, 모든 source triangle 꼭짓점의 컴파일 출력 좌표, 파트/tint/finite,
시위/화살 보존, 해시 검사4개 통과. 전체강제20task에서170 GameTest/128 JUnit 통과.
새 서버가 만든 팩의9개runtime asset과 JAR/소스의 byte 일치를 확인했다.
실제20TPS Arc(공격5회+이동), Void(aim+발사),5TPS Void(측면) native 입력 완료와
원본 framebuffer를 확인했다. source bowbody에검은 diffuse가 남아 원본의보라MATCAP 인상이
사라지는 문제를 발견했다. 이 첫 팩 결과는 최종색상 검증으로 세지 않는다.

자체 JVM 종료 후 source diffuse RGB를 보존하고 별도 저작 violet lift를 적용한다:
`r=55+.85r, g=12+.75g, b=110+1.15b`(반올림/255clamp).
원본 MATCAP/normal bake가 아니라 셰이더 불일치를 보완하는 명시적 팔레트 근사다.
신규5번째 JUnit이 검은/갈색 body 회귀를 검사한다. shape/손좌표/애니메이션은 변경하지 않는다.
최종 팩은 재생성/전체gate/새 서버·client로 다시 검사한다.

두 client와 연속PNG캡처 환경에서 actor FPS snapshot28~120을 관찰했다(Arc 종료37).
이 수치는 평균/p95/FPS보장이나 최대 다인 부하 통과가 아니다. 6894/4152파트 비용은 남으며,
단일세션 기능 통과와 별도로 프로파일링/LOD 또는 mesh batching경로의 후속 검토가 필요하다.

## S5: 추가 디테일 감소 없이 파트 비용 개선

재질 보정 후 첫 실제 Arc에서 단일client+연속PNG 환경에서도 FPS snapshot29~119,
종료33을 관찰했다. 최종안으로 바로 확정하지 않고 파트 비용을 수정한다.
stock java-mesh가 3개의 반크기 opaque quad로 채우던 삼각형을 **128² alpha right-triangle
texture를 입힌 full-size quad1개**로 바꾼다. MeshMath의 첫 affine matrix를 그대로 사용한다.
north/south UV를 반전하여 양면 공간상의 마스크가 일치한다. polygon/vertex/평균색 손실을
추가하지 않으며 raw3꼭짓점은 불변이다. 다만 대각선 경계는128texel cutout 근사이며
알파 필터링/밉맵과 edge aliasing은 실제 픽셀로 확인해야 한다.

지팡이6894→2298, 활4152→1384 mesh파트(각각66.7%감소). 이는 여전히 엔티티/드로콜 수가 아니다.
native codec/원좌표/양면UV/alpha mask/당김시위/해시/재질6JUnit과 전체gate를 재실행한다.
운영 선택모델ID는H28 유지하되 테스트JVM과 팩은 중지→재빌드→새JVM으로 갱신한다.
앞선3파트 pack/framebuffer는이후1파트 최종본의 근거로 재사용하지 않는다.
