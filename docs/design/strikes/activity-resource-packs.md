# 공격전별 리소스 팩

현재 악마의 소굴과 엑소더스의 추락은 공용 팩 위에 각자의 전용 팩을 적용한다. 공용 적 모델, 캠페인/공격전이 공유하는 효과음, 탐색기 아트, 두 공격전의 공용 강하 음악은 공용에 남긴다. 서버 월드 NBT는 클라이언트 팩이 아니다.

## 입장과 해제

1. 화력팀 출발 카운트다운 뒤 검은 로딩 화면을 유지한다.
2. 서버 월드 구성과 함께 전용 팩을 준비한다. R2 업로드와 파일 검증은 별도 작업 스레드에서 실행한다.
3. 정확한 현재 연결에 새 요청 UUID와 실제 ZIP의 SHA-1을 보낸다. 다운로드/적용 중인 상태를 로딩 화면에 표시한다.
4. `SUCCESSFULLY_LOADED` 응답과 기존 공용 팩 준비가 모두 확인된 화력팀만 배치한다. `ACCEPTED`와 `DOWNLOADED`만으로 이동하지 않는다.
5. 월드 이동 전 준비 중에는 `/화력팀 취소`로 취소할 수 있다. 거부/다운로드 실패/적용 실패/180초 초과는 입장을 중단한다.
6. 퇴장·취소·세션 종료 때 해당 연결과 실행이 소유한 전용 팩 UUID만 해제한다. 공용 팩과 다른 플레이어의 팩을 해제하지 않는다.
7. 재접속은 새 연결에 다시 요청한다. 이전 연결/요청의 늦은 응답으로 승인하지 않는다. 공용 팩 재로딩도 새 요청을 요구한다.

## R2와 배포 의존성

`rp-r2-uploader:1.1.0+26.3`의 공식 GitHub 릴리스 JAR를 전용 Ivy 저장소에서 받아 게임 JAR 안에 JiJ로 포함한다. 서버에 업로더 JAR를 따로 설치할 필요가 없다. 기존 단독 구버전 업로더 JAR가 있다면 중복 배치하지 말고 제거하거나 내장 버전 이상으로 맞춘다. Polymer의 기존 주 팩 경로는 유지한다.

운영 서버의 기존 `config/rp-r2-uploader.json` 자격 증명과 공개 주소를 그대로 사용한다. AutoHost가 `polymer:external`이면 생성한 전용 ZIP를 `R2ResourcePackUpload.uploadPack("destiny:<공격전 id>", path)`로 업로드하고, 성공한 결과의 주소/해시만 플레이어에게 보낸다. 이 기능이 생성·업로드하므로 같은 ZIP를 업로더 설정의 `additionalPacks`에 중복 등록할 필요가 없다. 별도의 파일을 올리는 업로더의 추가 팩 목록은 계속 사용할 수 있다.

자동/로컬 AutoHost 서버에서는 동일한 전용 ZIP를 기존 AutoHost에 등록한다. 이 경로로 격리 QA를 할 수 있으며, R2 업로드 검증과는 구분한다.

## 에셋 소유와 캐시

소유 목록은 `src/main/resources/destiny/pack/activities.json`에 있다. 압축 등 기존 변환이 끝난 최종 바이트를 분리하므로 원본 음원이나 모델을 수정하지 않는다. 혼합 `sounds.json`은 이벤트별로 나누며 같은 네임스페이스의 공용 등록을 덮어쓰지 않는다.

공용 ZIP의 `destiny/activity-pack-inputs.json`에는 전용 에셋 내용과 소유 목록의 지문도 포함한다. 따라서 전용 파일만 바뀌어도 공용 해시가 달라져 이전 전용 manifest와 혼용할 수 없다.

전용 ZIP와 원자적으로 갱신하는 manifest는 서버 실행 폴더의 `polymer/destiny-activity-packs/`에 있다. 파일 이름과 R2 주소에 실제 내용 해시를 넣는다. 공용 팩 시작 캐시를 복원할 때 전용 ZIP의 대응 공용 해시·파일 크기·실제 SHA-1도 검증한다. 누락/손상되면 전체 생성 경로로 돌아가며, 공용만 복원하고 전용 팩 없이 입장시키지 않는다.

클라이언트에 다운로드 캐시가 남아 있으면 재다운로드를 줄일 수 있지만 팩 적용/해제의 리소스 재로딩은 필요하다. 팩 준비 상태는 서버/연결/활동 실행별로 소유하며, 공유하는 것은 변경 불가능한 팩 배포 결과뿐이다.

배포 작업은 최대 두 개까지 병렬로 진행하며, 같은 서버의 같은 활동/공용 버전 요청은 하나로 합친다. 배포 실패 결과는 새 입장 시 다시 시도할 수 있어, 네트워크나 운영 설정 복구 후 서버를 재시작하지 않아도 된다.
