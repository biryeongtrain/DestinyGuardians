# W198 — 장전 포즈 밀도와 궁극기 보간

W197 원본 모션 적용 뒤 사용자가 장전과 궁극기 모두 끊기고 보간이 느리다고 지적했다. 동작 속도나 탄약·접촉 시각을 늘리지 않고 표시 갱신 경로를 수정한다. W197 QA는 당시 기능 검증과 사용자 피드백을 함께 봉인했으며 최종 화질 수락으로 취급하지 않는다.

## 원인과 선택

장전은 서버가 progress를 1/20 단위로 양자화하고 21개 정적 아이템 모델을 교체했다. 이자나기의 61틱 장전에서는 같은 모델이 약 3틱씩 유지된다. 바닐라 26.3 `RangeSelectItemModel.update`는 하나의 모델을 선택하고, `CustomModelDataProperty.get`은 현재 값을 그대로 읽는다. 모델 간 변환 보간은 없다. `transformation`도 bake 시 고정된다. 따라서 에이스와 이자나기의 포즈 뱅크·progress를 61샘플/60구간으로 늘려 매 서버 틱 새 포즈가 선택되게 한다. 이는 손 아이템의 60fps 연속 보간을 의미하지 않으며, 서버사이드 방식의 갱신 상한은 정상 TPS에서 약 20Hz다.

궁극기의 BetterModel은 서버 틱마다 25ms 포즈를 두 번 평가하고 두 자세를 연속 전송했다. Fabric `TransformationData.packDirty`는 매 변경 패킷에 `start_interpolation=0`을 넣어 클라이언트의 1틱 보간을 재시작한다. 두 원본 평가와 권위 서버 시계는 유지하면서 첫 중간 자세 전송만 억제하고 두 번째 도달 자세를 한 번 전송한다. 기존 1틱 보간 시간은 늘리지 않는다. 소유하지 않은 BetterModel tracker와 명시적 prime 경로는 보존한다.

## 분담과 기록

1. 26.3 merged jar와 BetterModel 3.5.1 bytecode를 읽어 아이템 모델 교체와 Display의 quaternion/partial-tick 보간을 구분했다. 새 클라이언트 모드는 추가하지 않는다.
2. 에이스·이자나기 generator/출력/검사는 별도 worktree에 배정했다. 현재 미커밋 기준선 68,272파일, SHA `ab18953481bc2cbf5a580d1cf295afd7ddf10ddc09f1b37564527f810b2ccfd1`을 복제했다. source-motion dataset·메시·UV·장전 시간은 유지한다.
3. master는 공유 selector, BetterModel sampling/publication, 실제 pipeline 전송 횟수 검사와 통합 Vision을 맡는다. `ServerPoseSampling`은 중첩·예외 때 publication 상태를 복구한다.
4. 에이스247개·이자나기729개 소유 delta를 기준 해시 검증 후 통합했다. 두 무기의 기존21자세는 새61샘플의 매3번째 위치에서 byte-identical이다. 무기 메시·UV와 W197 source dataset은 보존한다. 다른 무기의21샘플 장전 뱅크는 이번 변경 범위에 포함하지 않는다.
5. 통합 Python43개, generator 재현 에이스248개·이자나기803개·scope8개를 확인했다. W91 wrapper 변경에 따라 W162 입력 pin과 manifest만 갱신했으며 scope 제품7개는 이전과 byte-identical이다. 초기 시스템 Python/옛 HUD venv의 Pillow 부재와 그로 인한 stale scope pin 검사 실패도 QA에 남겼다. 번들 Python으로 재생성 후 targeted JUnit28개와 전체 JUnit1,961개·assemble가 통과했다.
6. 실제 BetterModel pipeline의 H20 clock 검사4개, 신규 갱신 검사3개, 기존 활 접촉·서버 시계 검사2개가 통과했다. 신규 검사는 에이스 실제 장전에서21개 초과 wire pose, 이자나기 일반/Honed 각각45개 초과 wire pose와61틱 commit, 틱당 최종 transform1회·내부 평가2회를 확인한다. 동일 검사의 중복 실행은 별개 제품 기능으로 세지 않는다.
7. 격리 Vision에서 장전4회·ADS5회와 이자나기 특수 장전, 아크 전개·공격·이동을 기록하고 실제 PNG를 확인했다. 에이스13발·이자나기4발 복구, 특수 장전 charge4, 아크 약4.23블록 이동과 카메라 복구를 확인했다. 특수 장전 발동은 명시적 서버 fixture이며 native Ctrl+Q 검증이 아니다.
8. 연속 PNG 저장 중 FPS 스냅샷이 일부18~44까지 내려가 캡처 부하를 분리했다. 캡처 없는 추가 장전·아크 시퀀스의 FPS 스냅샷은 각각57~60·53~58·54~60이었다. 이는 프레임 시간 백분위나60fps 애니메이션 보증이 아니다. 자동 검사는 갱신 경로와 타이밍의 근거이며, 손 아이템의 연속 보간이나 최종 모션 품질의 사용자 수락을 뜻하지 않는다.
9. 공허는 공격 입력 없이 한 번 시전해 후방 카메라·활/VFX·본인 카메라 복귀를 관측했다. 관찰 구간 끝121클라이언트 틱째 실제 사용자 입력으로 runner가 취소되어 완주 성공으로 세지 않으며 재시전하지 않았다. QA 채팅창 blocker는 저장 후 기존 자동 복구 허용 범위에서 닫았고, 추가 확인을 마친 뒤 본인 카메라·lease 없음·키/대기/실입력 중립을 확인했다.
10. 전체27시퀀스 중26완주·1취소와301장의 실제 framebuffer PNG를 [QA 기록](../qa/2026-10-27/w198/README.md)에 보존했다. 자기 서버/client·최대3,600초 awake coordinator와 caffeinate PID79367을 종료했고8102/25608포트가 비어 있음을 확인했다. W195/W196/W197의317/24/734개 봉인 파일 해시도 유지됐다.

## 유지 범위

원본 시계·장전 commit·탄약·아크 전개 .50s / 공격 .35s / 접촉 .10s를 유지한다. Shadowshot 자동 준비→발사와 나머지 클래스·모델도 같은 서버 시계 규약을 따른다. 원본에 없는 손 메시, 실린더 본 대응, source VFX 링크는 이 수정으로 해결했다고 주장하지 않는다.
